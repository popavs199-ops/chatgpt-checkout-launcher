# Subscription CRM dashboard as a GitHub Pages single-file app

A complete repo replacement: the old userscript launcher is gone, replaced by a static single-page CRM dashboard (`index.html`) backed by GitHub's Contents API as a database layer, plus a GitHub Actions workflow for expiration alerts via Discord webhook. The architecture is intentionally minimal: one HTML file with embedded Tailwind/JS, one JSON file as the data store, one cron workflow.

Watch for: GitHub PAT stored in localStorage with no scope validation or expiry awareness (confirmed). The write path to `database.json` is vulnerable to data loss under concurrent access despite a 409-retry message (confirmed). The expiration alert workflow silently succeeds when `WEBHOOK_URL` is unset, making misconfiguration invisible (confirmed).

## High-level view

The dashboard persists all subscription data by committing directly to `database.json` via GitHub's Contents API PUT endpoint. The SHA-based optimistic lock only detects conflicts after the fact; it does not retry, it just tells the user to try again and clears their form input — losing the data they tried to submit.

Credentials (a GitHub PAT with repo write access) live in localStorage in plaintext. The connection status indicator turns green the moment the fields are non-empty, before any API call confirms the token works. Any script on the same origin (including CDN-served Tailwind and Font Awesome) can read the stored token.

The prorating engine uses `(days / 30) * 170` with no ceiling or sanity check on date ranges. A typo in the end year commits an enormous amount to the database with no confirmation step. SAVE20's flat 20 DH discount against short periods (under ~3.5 days) yields a free subscription due to the zero-clamp.

The alerts workflow filters for Active records whose `endDate` matches exactly two days from now and posts a Discord embed. It exits 0 when the webhook secret is missing, so a misconfigured repo will appear healthy in the Actions UI indefinitely while never delivering an alert.

<summary>Issues (5)</summary>

1. **PAT exposure in localStorage** — The GitHub token is stored unencrypted in localStorage, readable by any script on the same origin (including injected CDN scripts). Consider using sessionStorage or prompting on each session.
2. **Connection status lies** — The "Connected" indicator activates when fields are non-empty, not after a successful API call. A revoked or mistyped token will show green until the first fetch fails.
3. **No write retry on conflict** — The 409 conflict path shows a toast and refreshes, but does not retry the write. Under concurrent use, the user's subscription data is silently lost.
4. **Silent alert misconfiguration** — When `NOTIFICATION_WEBHOOK` is unset, the Actions workflow logs a message and exits 0. The daily cron will appear healthy in the Actions UI indefinitely, masking a missing secret.
5. **Unbounded subscription amounts** — No validation caps date ranges; a typo in end date (e.g., 2035 instead of 2025) produces an enormous `amount` field committed to the database with no confirmation step.

## PAT handling and credential lifecycle

The GitHub PAT is stored under the key `crm_gh_token` in localStorage. Any JavaScript executing on the same origin can read it, including Tailwind's CDN script (`cdn.tailwindcss.com`) and Font Awesome's CDN. If either CDN is compromised or serves a supply-chain attack, the token is exfiltrated trivially. CDN supply-chain attacks have occurred in production (event-stream, ua-parser-js).

The `updateConnectionStatus` function sets the green indicator based solely on whether the three fields are truthy strings:

```javascript
updateConnectionStatus(token && owner && repo);
```

No API call validates the token. A user who just typed in credentials and clicked "Save Configuration" gets the green dot from `saveCredentials()` before `fetchData()` completes or fails.

## Data persistence via GitHub Contents API

The write path in `handleSubmit` performs a GET to retrieve the current SHA, appends the new record, then PUTs with that SHA. If a 409 is returned, it shows a toast and calls `fetchData()` but does not replay the write. The user's form data is cleared (`subEmail` is reset, dates are reset), so the subscription they just tried to add is gone from the UI with no mechanism to recover it.

The `btoa(JSON.stringify(records, null, 2))` encoding is fragile for non-ASCII email addresses. `btoa` throws on characters outside Latin-1. If a user enters an email with Unicode characters (valid per RFC 6531), the PUT will throw an unhandled exception inside the try block, which is caught generically as "Network error" — misleading.

## Prorating engine edge cases

The formula `(activeDays / 30) * 170` is linear and unbounded. No validation constrains `endDate` to a reasonable range. SAVE20 subtracts a flat 20 DH regardless of the prorated amount, so a 1-day subscription (price: ~5.67 DH) minus 20 goes negative, clamped to zero by `Math.max(0, finalPrice)`. This means SAVE20 grants a free subscription for any period under ~3.5 days — likely unintentional.

## Expiration alerts workflow

The workflow filters on exact date match (`endDate.getTime() === twoDaysFromNow.getTime()`). Both sides are normalized to midnight UTC, which is correct for `YYYY-MM-DD` strings. However, the dashboard stores dates from the browser's date input (local-date strings). A user in UTC+1 who creates a subscription ending "2025-06-15" means June 15 in their timezone, but the Actions workflow interprets it as UTC. This is a one-day-off risk depending on the operator's timezone relative to the 09:00 UTC cron.

The webhook failure path (`response.ok` is false) logs but exits 0. A consistently failing webhook (bad URL, expired token) will never surface as a workflow failure in the GitHub Actions UI. When `WEBHOOK_URL` is unset — the default state for any fork or fresh deployment — the workflow runs daily, succeeds, and never delivers an alert.

## Test coverage

There are no tests. The `calculatePrice` function has enough edge cases (zero days, negative results from SAVE20, unbounded date ranges) that even a minimal assertion file would catch regressions. The Actions workflow has no way to be tested short of triggering it with a crafted `database.json` and a real webhook URL.

Not tested: prorating formula, promo code discount math, date boundary conditions, conflict handling, Unicode in email fields, webhook failure paths.
